# リポジトリ構成

ファイルの追加・変更時に置き場所を判断できるよう、主要ディレクトリの責務と配置の考え方を示す。

## 配置の考え方

- 用途や実行環境に応じてディレクトリを分ける
  - アプリケーションの実装、公開コンテンツ、開発支援などの責務を明確にし、変更する場所を判断しやすくするため
- 同じ責務の中では、関連するものを近くに置く（コロケーション）
  - 記事と記事固有の素材などをまとめ、関連するものを一緒に確認・変更しやすくするため
- ツールの標準的な配置に従う
  - 独自の配置ルールや、それに伴う追加設定・説明を増やさないため

## ディレクトリ構成

主要ディレクトリの境界を示す。個別の設定ファイルや、各ディレクトリ内の詳細は省略する。

```text
.
├── .github/
├── content/
│   └── posts/
├── docs/
├── functions/
├── public/
├── scripts/
├── src/
└── tests/
    ├── src/
    ├── functions/
    └── e2e/
```

## ディレクトリの責務

- `.github/`
  - GitHub上のCIや依存関係更新など、開発・保守のための設定
- `src/`
  - Astro、React、スタイルなど、画面を構成する実装と関連するアプリケーションロジック
- `content/posts/`
  - 公開記事と記事固有の素材
- `public/`
  - ビルド時に加工せず公開する静的ファイル
- `functions/`
  - Cloudflare Pages FunctionsによるAPIと、関連するサーバー側ロジック
- `tests/`
  - Unit、Component、Functions、E2E、Visual Regressionのテストコードと、テスト専用のセットアップ
  - `tests/src/`は`src/`、`tests/functions/`は`functions/`のディレクトリ構成とファイル名を引き継ぐ
  - `tests/e2e/`はPlaywrightによるE2EとVisual Regressionテスト
- `scripts/`
  - ビルド、検査、生成に使うプロジェクト固有のスクリプト
- `docs/`
  - アーキテクチャ、開発、セキュリティに関する文書

### テストの配置

- テストコードは種別を問わず`tests/`へ集約する
  - アプリケーションの実装と検証用のコードを分け、テスト全体を一か所から確認できるようにするため
- `src/`を対象とするUnit／Componentテストは`tests/src/`、`functions/`を対象とするテストは`tests/functions/`に置く
  - 対象実装のディレクトリ構成とファイル名を引き継ぎ、実装側のパスから対応するテストの配置先を判断できるようにするため
  - テスト種別ごとに独自の階層を増やさない
- E2EとVisual Regressionテストは`tests/e2e/`に置く
- テスト専用のヘルパーやセットアップも`tests/`配下に置く
  - 複数種別で共有するセットアップは`tests/setup.ts`、E2E専用のヘルパーは`tests/e2e/helpers/`に置く
- アプリケーションの実行時にも使用するコードやデータは、テスト専用として`tests/`へ移動しない
  - 開発サーバーとテストビルドで公開する`src/test-fixtures/`は`src/`に残す

## プロジェクト境界と設定

- リポジトリルートをAstroとCloudflare Pagesのプロジェクトルートとする
  - Astroによる画面とCloudflare Pages FunctionsによるAPIを一つのアプリケーションとして管理し、ビルド・デプロイの単位とプロジェクト境界を合わせるため
- プロジェクト全体に作用する設定は、各ツールの標準的な配置に従う
  - 設定ファイルの数や見た目の整理よりも、ツールが想定する方法で設定を発見・利用できることを優先する
- ビルド・デプロイや依存関係を独立して管理する必要が生じた場合に、プロジェクト境界とディレクトリ構成を見直す
  - 管理単位の変化に合わせて境界を分け、変更の影響範囲を明確にするため
