# Pull Request作成ガイド

## 言語

- Pull Requestのタイトルと本文は日本語で書く
- コマンド、ファイルパス、識別子などは原文の表記を維持する

## ブランチ名

ブランチ名は、変更の種類が分かるSemantic Branch Names形式にする。

```text
<type>/<short-description>
```

- `type`には`feat`、`fix`、`docs`、`refactor`、`test`、`chore`、`design`のいずれかを使用する
  - `design`は、デザイン仕様と見た目の変更を同時に扱う場合に使う
- `short-description`は変更内容を表す英語のkebab-caseにする
- `main`へ直接コミットせず、変更内容に対応するブランチからPRを作成する

例: `feat/home-search`、`fix/rss-published-date`、`docs/development-setup`

## タイトル

変更の目的が分かる簡潔なタイトルにする。

例: `コンポーネントを機能単位で整理`

## 本文

本文は、目的から要件、設計、実装へと、抽象から具体の順に書く。レビュアーが、目的に対してどの手段を採用したか、その手段がなぜ適切かを追って判断できるようにするため。

本文の書き方は、すべてのPRで従う構成と、PRの内容に応じて書き手が選ぶ型に分ける。この節は前者を定める。後者は[選んで使う型](#選んで使う型)にまとめる。

```markdown
## 概要

## 変更内容

### 要件

### 設計

### 実装

### 検討した代替案

## 観測方法

### マージ前に確認したこと

### マージ後に確認すること

## レビュー観点
```

| 見出し | 扱い | 内容 |
| --- | --- | --- |
| 概要 | 必須 | 変更の目的と背景 |
| 要件 | 必須 | 目的を達成するために満たす条件 |
| 設計 | 必須 | 要件に対して採用した手段と、その手段が適切な理由 |
| 実装 | 必須 | 設計した手段を実現する具体的な変更 |
| 検討した代替案 | 比較した案がある場合 | 採用しなかった案と、その理由 |
| マージ前に確認したこと | 必須 | 実施した確認と結果 |
| マージ後に確認すること | 本番やデプロイに影響する場合 | 目的を達成できたかを確かめる手順と観測点 |
| レビュー観点 | レビュアーが判断する点がある場合 | 判断の対象と、その根拠の所在 |

誤字の修正や依存関係の更新のように手段を選ぶ余地がない変更では、変更内容の小見出しを省き、変更点だけを書く。

### 書き方

- 概要は、以降を読まなくても目的と背景が分かるようにする。見出しのない冒頭の要約は置かない
  - 概要と内容が重複するため
- 概要に手段を書かない
  - 目的と手段を分けると、手段の妥当性を目的に照らして判断できるため
- 要件は、採用する手段ではなく、満たすべき状態として書く
  - `一時ディレクトリへビルドする`ではなく、`テストは配信する成果物を書き換えない`と書く
- 設計は、手段ごとに、どの要件をなぜ満たすかを書く。手段が複数ある場合は表にする
- 実装はコミット一覧を再掲しない。設計した手段ごとに、変更したファイルと仕組みを書く
- 検討した代替案には、実際に比較した案だけを書く。採用しなかった理由を、要件に照らして書く
- 観測方法にはログ全文を貼らない。何を確認したかと結果だけを書く
  - CIの詳細はChecksに残るため
- マージ後に確認することには、本番で確認するURLや画面、ワークフローの結果を具体的に書く
- レビュー観点は末尾に置く
  - 目的から実装までを読んだ後で判断する点だから
- レビュー観点は、レビュアーへの依頼ではなく、観点そのものとして書く
  - `〜を見てほしい`ではなく、`〜という認識の妥当性`のように判断の対象を書き、根拠の所在を続ける
  - 既知の制約を並べるだけにしない。制約は、どの判断に関わるかと合わせて書く
- `## 詳細`という見出しは使わない
  - 範囲が曖昧で、実装したことの全列挙になりやすいため
- 実装が長くなる場合は、要点を先に書き、内訳を`<details>`で折りたたむ
- 数値を根拠にした判断は、実測値を表で示す

### スクリーンショット

- 見た目が変わる変更では、観測方法に画像を貼る。文章だけで再現できない
- `gh pr edit --attach`でアップロードする。本文中の`![alt](./file.png)`参照が、アップロード先のURLへ書き換わる
- before/afterは同じ幅・同じテーマで撮影する
- 一時的なプレビュー環境のURLは貼らない。マージ後に実態と乖離する一方で、PRは記録として残り続ける
- 外部の告知や仕様を根拠にする場合は、リンクに加えて、根拠になる部分だけを切り抜いた画像を貼る
  - ページ全体の画像では、どこが根拠かが分からないため
  - リンク先が更新されても、判断した時点の根拠が残るため

レビュー準備が完了していない場合はDraft PRとして作成する。

## 選んで使う型

PRの内容に応じて、書き手が使うかを決める型をまとめる。使わなくても、本文の構成は満たせる。

### レビュー観点を3段に分ける

手段を選ぶ余地があり、レビュアーが判断する点が複数ある場合に使う。レビュー観点を、本文の抽象から具体への順に合わせて3段に分ける。

| 見出し | 対応する本文 | 判断の対象 |
| --- | --- | --- |
| 問題の認識は適切か | 概要 | 目的と背景の捉え方が、根拠に照らして正しいか |
| アプローチは適切か | 要件、設計、検討した代替案 | 要件に対して選んだ手段と、受け入れる代償が妥当か |
| 実装の設計は適切か | 実装 | 範囲、置き場所、条件などの設計上の判断が妥当か |

- 見出しは問いの形で書く
- 各見出しの下は、何の妥当性を問う観点かを1文で書き、根拠の所在、推論に留まる点、受け入れる代償を箇条書きで続ける
- 該当する判断がない段は省く

例:

```markdown
### 問題の認識は適切か

`ubuntu-latest`の26.04移行で、CIと本番deployのChromiumインストールが失敗するという認識の妥当性。

- 移行の時期は、概要の移行案内のスクリーンショットが根拠になる
- 失敗するという判断は、Playwright 1.57.0の配布定義に`ubuntu26.04-x64`がないことが根拠になる
- 26.04のランナーでの実測はなく、ソースからの推論に留まる
```

### 概要をIssueへの参照で済ませる

目的と背景がIssueに書かれている場合に使う。概要にはIssueへのリンクと目的を1文で書き、背景はIssueに任せる。

- 同じ背景をPRとIssueの両方で管理しないため
- Issueの背景と変更の範囲が異なる場合は使わない。概要に差分を書く
