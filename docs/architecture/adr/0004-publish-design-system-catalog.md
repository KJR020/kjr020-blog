# 確認用カタログの公開

開発サーバーだけで表示していた確認用カタログを、本番サイトで公開した判断を記録する。

## 決定

確認用カタログを本番サイトの`/design-system`で公開した。検索エンジンには索引させず、HeaderのNavigationからリンクする構成とした。

## 背景

カタログは開発サーバーだけにルートを登録し、公開成果物へ出力しない方針だった。仕様書には`build`で登録しないことと、`noindex,nofollow`を指定することを定め、更新フローでも`dist/design-system`が生成されないことを確認していた。

カタログは実装と同じトークンとコンポーネントから描画するため、閲覧にはリポジトリの取得と開発サーバーの起動が必要だった。実装と接続した仕様を、リポジトリを開かずに参照できるようにするため、この方針を覆した。

## 公開の形

- 本番と同じビルドと同じWorkerで配信した
- 別のURLや別のデプロイは採用しなかった
  - 別にデプロイすると、本番の実装とカタログの版がずれることがあるため
  - ビルド、デプロイ、DNSの管理対象が増えるため

## 検索エンジンとサイト内の導線

- `noindex,nofollow`を残し、sitemapから除外した
  - `noindex`を外す案は採用しなかった。標本の文言や架空のデータが検索結果に出て、記事と流入を奪い合うため
- HeaderのNavigationに`Design System`を追加した
  - URLを知っている人だけが見る案、フッターからリンクする案と比較し、Headerを選んだ
- 48remではHeaderに全項目が1行に収まらないため、60rem未満ではSearchの`⌘K`表示を省いた
  - ラベルを`Design`に縮める案は、移動先が具体的でなくなるため採用しなかった
  - 横並びに切り替える幅を広げる案は、Grid systemのBreakpointと揃わなくなるため採用しなかった
- Pagefindの索引とRSSには含めなかった
  - 既存の構成で記事だけが対象になっており、変更は不要だった

## 標本データ

- Scrapbox Card Listの標本を、実在するCosenseのページから`example.com`の架空のページへ置き換えた
  - 実在するページに、標本用に書いた説明と更新日を添えて公開することになるため
- Post List Itemの標本は、公開済みの最新記事を使い続けた
  - すでに公開している内容であり、実データでの表示崩れに気づけるため

## 結果と制約

- カタログは本番のデプロイごとに更新され、本番と同じ版の実装を表示する
- カタログの文言も公開する内容になり、UIライティングガイドラインの対象になる
- `pnpm build`の後処理で、カタログの出力と`noindex,nofollow`、Pagefindの索引対象外であること、sitemapとRSSへの非掲載、テスト用fixtureの非出力を検査する
  - 検査に失敗するとビルドが失敗し、デプロイされない
