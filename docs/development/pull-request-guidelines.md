# Pull Request 作成ガイド

## 言語

- PRのタイトルと本文は日本語で記述する。
- コマンド、ファイルパス、識別子などは原文の表記を維持する。

## ブランチ名

ブランチ名は、変更の種類が分かるSemantic Branch Names形式にする。

```text
<type>/<short-description>
```

- `type`には`feat`、`fix`、`docs`、`refactor`、`test`、`chore`のいずれかを使用する。
- `short-description`は変更内容を表す英語のkebab-caseにする。
- `main`へ直接コミットせず、変更内容に対応するブランチからPRを作成する。

例: `feat/home-search`、`fix/rss-published-date`、`docs/development-setup`

## タイトル

変更の目的が分かる簡潔なタイトルにする。

例: `コンポーネントを機能単位で整理`

## 本文

冒頭に1〜2文の要約を置き、そのあとを次の見出しで構成する。毎回すべてを埋めるテンプレートではなく、該当する節だけを使う。

| 見出し | 扱い | 内容 |
| --- | --- | --- |
| レビュー観点 | 重点的に見てほしい点がある場合 | レビュアーに判断してほしい点 |
| 背景 | 原則書く | なぜこの変更が必要なのか |
| 変更内容 | 原則書く | このPRによって何が変わるか |
| スクリーンショット | 見た目が変わる場合 | before/after |
| 検証 | 原則書く | 実施した確認と結果 |
| 影響・制約 | 非自明な影響や後続Issueがある場合 | 利用者・開発者への影響、既知の制約 |

通常のPRは「要約・背景・変更内容・検証」の4ブロックで足りる。

### 書き方

- 冒頭の要約は、見出し以降を読まなくても変更の骨子が分かるようにする。`## 概要`という見出しは置かない。要約と重複する
- レビュー観点を先頭付近に置く。読み終わってから見るべき場所が分かるのは、レビューの導線として逆になる。CodeRabbitに対してもレビュー範囲を先に渡せる
- 変更内容はコミット一覧を再掲しない。変更を意味のある単位で要約する
- 検証はログ全文を貼らない。何を確認したかと結果だけを書く。CIの詳細はChecksに残る
- `## 詳細`という見出しは使わない。範囲が曖昧で、実装したことの全列挙になりやすい
- 変更内容が長くなる場合は、要点を先に書き、内訳を`<details>`で折りたたむ。先頭から通して読める分量を保つ
- 数値を根拠にした判断は、実測値を表で示す

### スクリーンショット

- 見た目が変わる変更では画像を貼る。文章だけで再現できない
- `gh pr edit --attach`でアップロードする。本文中の`![alt](./file.png)`参照が、アップロード先のURLへ書き換わる
- before/afterは同じ幅・同じテーマで撮影する
- 一時的なプレビュー環境のURLは貼らない。マージ後に実態と乖離する一方で、PRは記録として残り続ける

レビュー準備が完了していない場合はDraft PRとして作成する。
