# ドキュメント執筆ガイドライン

`docs/`配下の文書の位置づけ、構成、表記を定義する。

## Living Standard

`docs/`配下の文書はLiving Standardとして扱う。文書は常に現在の仕様を表し、過去の経緯や未確定の予定を持たない。

- 版数、改訂履歴、最終更新日を文書に書かない
  - 変更の履歴はGitが持ち、文書が二重に持つと必ず食い違うため
- 「未対応」「TODO」「今後の予定」の節を置かない
  - 決まっていないことは書かず、決まったら仕様として書くため
  - 対応が必要な事項はIssueで追跡する
- 「〜になりました」「〜に変更した」と書かず、現在の状態だけを書く
- 仕様が変わったら、差分を追記せず該当箇所を書き換える
- 実装が文書と食い違ったら、どちらが正しいかを決めて一方を直す。両論を併記しない

### 現在の理由は書き、過去の経緯は書かない

現在の仕様を理解し、変更を判断するために必要な理由は現在の事実として扱う。そこへ至った変更の経緯は書かない。

- 書く: `- APIレスポンスをキャッシュする` / `  - Cosense APIへのリクエスト数を抑えるため`
- 書かない: `以前はキャッシュしていなかったが、アクセス数が増えたため追加した`

経緯は次のどちらかに書く。

- 選択肢を比較して方針を決めた記録は、意思決定ログ(ADR)に書く
  - 却下した案と却下の理由が、後から同じ検討を繰り返さないために要るため
  - `docs/architecture/`に置く。[コメント機能: Giscus採用](../architecture/comment_architecture.md)が例
- 個別の変更の背景と対応状況は、Issueに書く

意思決定ログはLiving Standardの対象外とする。ある時点の決定を記録するものであり、現在の仕様を表す文書ではない。決定の結果として現在有効な仕様は、対応する仕様文書に書く。

### 残存リスクは現在の状態として書く

現在の仕様で解消していないと分かっている制約やリスクは「残存リスク」として書いてよい。未確定事項ではなく、現在の仕様が何を守らないかという事実である。

- 対応案、対応予定、期限は書かない
  - 予定はLiving Standardの対象外であり、Issueで追跡するため

## 構成

### 文書

1. H1は文書の名前だけを書く
2. 空行を挟み、その文書が何を定義するかを1〜2文で書く
3. 見出しは`##`から始め、`###`までとする。`####`以下は使わない

```markdown
# Cosense API Proxy

Cosenseの記事情報を、秘密情報をBrowserへ公開せずブログに提供するための構成を定義する。

## 概要
```

節の名前は内容から決める。よく使うものは「概要」「全体像」「用語」「関連ファイル」「参考資料」。

実装ファイルや他の文書への参照が必要なら、末尾に「関連ファイル」を置き、リンクと1文の説明を並べる。外部の一次情報は「参考資料」に分ける。

### README

- 各ディレクトリの`README.md`は目次として置く
- H1にはカテゴリ名を書く
- H1の直後に、そのカテゴリが扱う内容を1文で書く
- 「## 文書一覧」に各文書へのリンクと1文の説明を並べる
- 読む順序に意味がある場合だけ「## 読む順序」を置く

### 文書を分ける基準

- 1つの文書は1つの関心事を扱う
- 参照する場面が違うものは別の文書にする
- 節を足すか新しい文書を作るかは、その節だけを読みに来る場面があるかで決める

## 箇条書き

### 個別に判定する項目が複数あるときは箇条書きにする

独立して適否を判断する項目が複数あるなら、段落に溶かさず箇条書きで並べる。

- いくつあるかが一目で分かる
- 項目を追加・削除するときに、他の項目を読み直さずに済む
- 実装やレビューで1項目ずつ照合できる

判断の単位が1つなら段落で書く。「認証にはCookieを使う」と「CookieにはHttpOnlyを付ける」は別々に適否を判定するので2項目。「Cookieを利用し、ブラウザに認証状態を保持する」は1つの説明なので段落でよい。

段落は、箇条書きの前に置いて前提を述べるためにも使う。何をなぜ定めるかを段落で示し、個々の規則を箇条書きで並べる。

順序に意味がある手順や構成だけ番号付きリストにし、それ以外は箇条書きにする。

### 親に規則、子に補足を置く

インデントは意味の従属を表す。

- 親項目には、独立して適否を判断できる規則を書く
- 子項目には、その規則だけに従属する理由、適用条件、例外、具体例を、必要な場合だけ置く
- 並列な規則は子項目にせず、同じ階層に置く
  - 親子関係を読んだ人が従属関係だと解釈するため
- 階層は2段までにする
  - 3段目が必要になるのは、親項目が複数の規則を含んでいる場合が多いため

`repository-structure.md`の「配置の考え方」が典型例。

```markdown
- 用途や実行環境に応じてディレクトリを分ける
  - アプリケーションの実装、公開コンテンツ、開発支援などの責務を明確にし、変更する場所を判断しやすくするため
- 同じ責務の中では、関連するものを近くに置く(コロケーション)
  - 記事と記事固有の素材などをまとめ、関連するものを一緒に確認・変更しやすくするため
```

### 理由は判断材料になるときだけ書く

判断の背景が自明でなく、将来仕様を変更するときの判断材料になる場合は、子項目に理由を書く。表記規則や事実には理由を付けない。

理由を全項目に付けると、「表記を統一するため」のような情報量のない行が増え、本当に必要な理由が埋もれる。

理由を書く場合は「〜するため」で終える。規則と理由が視覚的に分かれ、規則だけを拾い読みできる。

### 1項目には独立して判定する規則を1つだけ書く

「かつ」「また」「ただし」で複数の要求をつないでいる項目は、分けられないか確認する。条件や例外であれば子項目に下げる。

機械的に分割しない。「AかつBの場合だけCを許可する」のように、分けると意味が変わるものは1項目のままにする。

### 原則は見出し、段落、箇条書きの3層で書く

複数の原則を定義する文書では、原則ごとに見出しを立てる。

- 見出しは原則そのものを一文で書く
  - `### 5. 網羅的な体系の構築より、継続して改善できる規模を優先する`
  - 番号を振ると、他の文書から「原則5」と参照できる
- 見出しの直後の段落で、その原則が何を守るかを述べる
- 箇条書きで個別の適用規則を並べる

### 対応関係は同じ形をそろえる

「名前と内容」を並べる場合は、すべての項目を同じ形で書く。

- 2項目の単純な対応は箇条書きにする
- 3列以上の比較や、行と列を交差して参照するものは表にする

## 記法

### 箇条書きの句点

- 項目の末尾に句点を付けない
- 項目の中で文を切る場合は、文中の句点を残して末尾だけ落とす

### 表

判断基準や対応関係のように、列が揃うものだけを表にする。列が揃わないものは箇条書きにする。

区切り行は`| --- |`で書く。

### 図

構造や流れを言葉で書くと追いにくい場合だけMermaidを使う。図は本文の代わりではなく、本文の理解を助けるために置く。

### コードとコマンド

コードブロックには言語を指定する。シェルは`shell`、Markdownの例は`markdown`を使う。

設定ファイルに定義された値や設定内容を、文書側に複製して管理しない。文書には設定の目的と参照先を書き、実体は設定ファイルをSource of Truthとする。実行手順としてコマンドを載せることは、これに当たらない。

## 表記

- 日本語と英数字の間にスペースを入れない
  - 例: `Pages Function`の入力、`src/`配下
- インラインコードと日本語の間にもスペースを入れない
- 括弧とコロンは半角の`()`と`:`を使う
  - 前後にスペースを入れない。コロンの後ろだけスペースを1つ置く
- 固有名詞は提供元の表記に従う。Cosense、Cloudflare Pages、Astro、Biome
- ファイル名、パス、コマンド、設定キー、環境変数、識別子はバッククォートで囲む
  - `package.json`、`src/`、`pnpm check:links`、`allowBuilds`、`SCRAPBOX_SID`、`validateProject()`

## リンク

- リポジトリ内の参照は相対リンクで書く
  - `pnpm check:links`がCIで検査するため
- パスに`[`や`]`を含む場合はURLエンコードする
  - 例: `functions/api/pages/%5Bproject%5D.ts`
- リンクテキストはファイル名ではなく対象の名前にする
